# Асинхронные обработчики (АО) и элементы очереди (QI)

АО выполняют длительные операции в фоне: не блокируют UI, распараллеливают пакетную обработку из ФП, выполняют отложенную логику после сохранения сущности.

**Как распознать АО:** метод `public virtual void {Имя}(AsyncHandlerInvokeArgs.{Имя}InvokeArgs args)` в `ModuleAsyncHandlers.cs`. Запуск: `AsyncHandlers.{Имя}.Create()` → заполнение свойств → `.ExecuteAsync()`.

**Как распознать QI:** сущность `*QueueItem`, наследник `Sungero.CoreEntities.DatabookEntry`, со свойством `ProcessingStatus`. Набор значений статуса задаётся в метаданных конкретной очереди и у разных очередей различается.

## Архитектура АО

- Для АО создаётся справочник с элементом очереди (QI) для контроля и хранения состояния (практически всегда обязателен).
- Метод АО — тонкий оркестратор: лог старта, guard-clauses, делегирование в `Functions.*`, явная установка `args.Retry` в финальной ветке, лог завершения. Нетривиальная логика — в `ModuleServerFunctions`.
- Для сложных сценариев — context-структура (`Structures.Module.I*HandlerContext`), наполняемая из QI и связанных сущностей и возвращающая флаги `NeedRetry` / `IsValid`. Для простого АО из нескольких строк не обязательна.

## Логирование

- Старт: `"MyHandler start. QueueItemId = {0}, Retry = {1}."`.
- Штатные ветки (QI не найден, блокировка, пропуск) — `Debug`; реальные сбои — `Error`/`ErrorFormat` с полным объектом исключения.
- При большом объёме логов — `Logger.WithLogger("MyHandler")` или постфикс-логгер.

## Управление retry

- В начале метода явно `args.Retry = false`, иначе платформа может повторить АО по умолчанию.
- Ошибки делятся на два класса и обрабатываются **разными** `catch`:
  - **Исправимые** (временный сбой): `RepeatedLockException` и похожие конкурентные исключения платформы. Действие: увеличить `QueueItem.Retries`, при необходимости задать `args.NextRetryTime`, `args.Retry = true`, выйти.
  - **Фатальные** (логическая ошибка или некорректные данные): `NullReferenceException`, `InvalidOperationException`, `AppliedCodeException` и любые неожиданные. Действие: QI в статус `Error`, причина в `QueueItem.Note`, лог `Error` с полным исключением, `args.Retry = false`, выйти. Повтор бессмыслен.
- Отложить следующую попытку на время — `args.NextRetryTime`.

## Взаимодействие с QI

- Перед `ExecuteAsync()` в Job/Functions QI переводится в `InProcess` и сохраняется: это предотвращает гонку при параллельных запусках.
- Внутри АО смена статуса — методами самой сущности (`SetProcessingStatusInProcess`, `SetProcessingStatusProcessed`), а не прямым присвоением поля.
- После длительных операций и `Transactions.Execute` QI переполучать из БД: NHibernate-сессия могла быть сброшена.
- QI не найден по `args.QueueItemId` → Debug-лог и `return`, без исключения.
- Связанная сущность (документ, задача) удалена → удалить QI и `return`.

## Идемпотентность

- Workflow-сценарии: проверка, например, `TaskStartId`; не совпал с текущим — завершиться без работы.
- Пакетная обработка: `AsyncHandlerId` или `LaunchId`; не совпал — QI в `Processed` без обработки.
- Если два экземпляра АО могут стартовать для одной сущности, АО проверяет, не запущен ли он повторно, и завершается. Рекомендация для исключительных случаев, когда стандартных механизмов защиты не хватает.

## Транзакции и финализация

- Транзакция в АО — только при обоснованной необходимости атомарности (например, генерация PublicBody + смена статуса); всю логику одной транзакцией не оборачивать. После `Transactions.Execute` сущности переполучать, если они используются дальше.
- Если QI должен быть удалён при любом исходе — удаление в `finally`. При успехе QI всегда удаляется.
- Восстановление «зависших» QI (застрявших в `InProcess`) — задача фонового процесса, а не АО: он возвращает такие записи в `Scheduled` или `Suspended`.

## Элемент очереди (QI)

- Для каждого типа АО — отдельный тип QI, наследник `Sungero.CoreEntities.DatabookEntry`.
- Приоритеты — именованные константы в `{Сущность}Constants.cs` (`Priorities.Default`, `Priorities.Low`). Начальный приоритет ставится в `Created` через вызов функции, а не прямым присвоением.
- Смена `ProcessingStatus` — в методах сущности QI (`SetProcessingStatusInProcess`, `SetProcessingStatusProcessed`, `SetProcessingStatusSuspended`); прямого присвоения `_obj.ProcessingStatus = ...` снаружи нет. Это для новых QI и очередей, где такие методы уже есть; в существующих очередях без методов-обёрток прямое присвоение допустимо.
- Каждый метод смены статуса вызывает `_obj.Save()` и перехватывает исключение с логом `Debug`: ошибка сохранения не прерывает АО, метод возвращает `false`.
- Удаление QI — в статическом методе с проверкой `queueItem != null`. Удалять после успешного завершения или когда обработка неактуальна; в остальных случаях QI остаётся в БД для прозрачности.
