# Проектирование функций и точек расширения

В прикладном решении нельзя объявлять собственные классы и интерфейсы. Единица проектирования — **функция** (экземплярная или модульная) и **иерархия типов сущностей** в метаданных.

## Где разместить метод

- Слой выбирается по `rx-code-kinds`. Экземплярные функции — `{Сущность}{Server|Shared|Client}Functions`, модульные — `ModuleFunctions` того же вида кода.
- Метод получает одну сущность, работает именно с ней, и она обязательна → экземплярный метод сущности.
- Метод получает несколько сущностей, обрабатывает набор или сущность не нужна → модульный метод.
- В `actions`, `handlers` и `jobs` — только верхнеуровневая оркестрация, новые вспомогательные методы там не создавать. Низкоуровневая реализация уходит в экземплярные или модульные функции.
- Фоновые процессы обслуживания сущности размещать в модуле, где объявлена сущность, если нет явной причины для другого модуля.
- Функциональность группировать регионами `#region`; модульные методы — в отдельном регионе. Имя региона описывает назначение кода, а не уровень доступа.

## Область видимости, virtual, атрибуты

- Новый метод по умолчанию `private` и `static`, если не обращается к экземплярным членам. В классах `{Сущность}Functions` `static` не ставить: он меняет контракт вызова через фасад (сущность перестаёт быть первым аргументом).
- `public virtual` — только если метод задуман точкой расширения (его будут переопределять в решении заказчика или в сущности-наследнике). `virtual` «на всякий случай» не ставить: после переопределения заказчиком сигнатура заморожена.
- Не расширять видимость до `public` / `[Public]` ради теста: мок-платформа подменяет и вызывает и непубличные методы.
- `[Public]` — только при реальном межмодульном использовании.
- Серверные функции для клиента — `[Remote]`; если состояние не меняется — `[Remote(IsPure = true)]`.

## Совместимость сигнатур

Функции `public virtual`, `[Public]`, `[Remote]` — контракт решения. `override` в C# требует точного совпадения сигнатуры, любое изменение ломает сборку решения заказчика.

**Новая расширяемая функция**
- Параметры-режимы и набор полей одного предмета передавать прикладной структурой, а не отдельными аргументами (`bool needSave, bool withNotice, bool isRepeat` — признак неверного дизайна). Поле в структуру добавляется без изменения сигнатуры. Пример: `GenerateSellerTitle(Structures.AccountingDocumentBase.ISellerTitle sellerTitle)`.
- Проверка или валидация, у которой возможен отказ с причиной (`Validate*`, `Check*`), возвращает структуру с результатом и причиной, а не `bool`/`null`. Образцы: `Structures.ApprovalFunctionStageBase.ExecutionResult` (`Success`, `Retry`, `ErrorMessage`), `Structures.ConditionBase.ConditionResult` (`Branch`, `Message`).
- Простой предикат (`Is*`, `Has*`, `Can*`) без причины отказа остаётся `bool`.

**Изменение существующей функции**
- Не менять сигнатуру существующей `public virtual` / `[Public]` / `[Remote]` функции: параметры, типы, порядок, тип возврата, имя. То же для публичных свойств и констант.
- Параметр со значением по умолчанию совместимость **не сохраняет**.
- Расширять новой перегрузкой, а старую оставить и реализовать вызовом новой с прежним поведением. При необходимости пометить старую `[Obsolete]` с указанием замены и версии и перенести в `Obsolete*.cs`.
- Смысл возвращаемого значения существующего метода не менять и не расширять новыми типами результата: для нового типа — отдельный метод.
- `[Obsolete]` на публичный метод — только по согласованному решению с путём миграции.
- Удаление или изменение публичного API фиксировать записью о breaking change во внутреннем changelog (только пользовательски значимые изменения).

## Тестируемость

- Бизнес-правило проверяется отдельно от операции: расчёт, правило или преобразование выносится в функцию «данные на входе — результат на выходе». Выборка, правило и изменение состояния в одном теле — плохо.
- Результат наблюдаем: метод, который проверяет или вычисляет, возвращает значение или структуру, а не только пишет в лог или молча меняет поле.
- Нет скрытого состояния между вызовами: никаких статических изменяемых полей и самодельных кэшей уровня класса.

## SOLID для функций и сущностей

- **SRP.** Одна функция — одна задача: получить данные, или вычислить, или изменить состояние. Последовательность вызовов остаётся у вызывающего (действие, обработчик, ФП, АО). Признаки нарушения: блоки с комментариями-заголовками, «и» в имени (`SaveAndNotify`), `summary` не умещается в одну фразу.
- **OCP.** Если код базового типа ветвится по типу наследника (`Contracts.Is(_obj)`, сравнение GUID типа) — вынести логику в `virtual`-метод базового типа и `override` в наследнике. Новая разновидность поведения — новый `override`, а не наращивание `switch`/`else if`. Не требуется, если ветка решает о самом базовом типе или тип наследника недоступен базовому модулю по зависимостям. Ветвление по значению перечисления (`LifeCycleState`, вид документа) этим правилом не охвачено: значение не связано с типом.
- **LSP.** `override` сохраняет смысл возврата, гарантии по `null` и пустым коллекциям, не бросает исключений там, где база возвращала значение, не сужает входные данные. Дополняешь — вызывай `base.{Метод}(...)`; заменяешь целиком — только если база неприменима, причину укажи комментарием. `override`, который лишь вызывает `base` без изменений, не нужен (кроме заготовок DS в `*Actions.cs` и `*Handlers.cs`).
- **ISP.** Структура-параметр и структура-результат описывают один предмет; если половина полей в сценарии не используется — разделить. Точка расширения передаёт переопределяющему всё нужное параметрами, чтобы `override` не доставал данные из params карточки, статического состояния или повторным запросом. Не заставлять вызывающего готовить данные, которые метод может получить из переданных аргументов.
- **DIP.** К другому модулю — только через `PublicFunctions`, `PublicConstants`, `[Public]`-структуры; не копировать его логику и SQL. Сторонние библиотеки — в `Isolated`, бизнес-логика не оперирует их типами. Обращение к внешней системе — отдельная функция, возвращающая прикладной результат.
