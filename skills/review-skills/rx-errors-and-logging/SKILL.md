# Обработка ошибок и логирование

## Ошибки

- Ошибки обрабатываются явно и логируются через `Logger`.
- Прикладные исключения — `AppliedCodeException.Create(...)`. Родные исключения .NET (`ArgumentOutOfRangeException` и т. п.) не бросать и не перехватывать.
- Ожидаемые пользовательские и бизнес-ошибки — `e.AddError` / `e.AddWarning` в обработчиках или `args.AddError` в диалогах и клиентских функциях, а не `throw AppliedCodeException`.
- Клиентский метод с диалогом сообщает пользователю через `Dialogs.NotifyMessage`, а не добавляет сообщение в `ValidationResult` сущности.
- Предусловия, зависящие от состояния документа или сущности, проверять заранее и завершаться штатным сообщением, а не исключением.
- Не перехватывать `catch (Exception)` без явной причины; ловить конкретные ожидаемые типы.
- В `Showing` не допускать необработанных исключений: карточка должна открываться даже при сбое блокировки или вспомогательной логики.
- Пробрасывать через `throw`, а не `throw ex`. Новое исключение вместо пойманного — только с `InnerException`.
- В `catch` передавать в лог полный объект исключения отдельным аргументом: `Logger.Error(message, ex)`, `Logger.ErrorFormat(format, ex, ...)`, а не только `ex.Message`.
- Блок `try` охватывает только код, который может бросить исключение. Ожидаемые прикладные исключения не бросать внутри `try` с широким `catch`.
- Бросить исключение и сразу поймать его в том же методе нельзя. Созданное исключение нужно выбросить, а не оставить неиспользованным объектом.
- Вспомогательные методы валидации возвращают структуру-результат с ошибкой.
- В однотипных методах и перегрузках — один контракт ошибок: либо исключение, либо nullable/default. Не смешивать без причины.
- Пустой успешный результат, ошибка и непустой результат — отдельные ветки: не подменять пустой список общим `catch`, не использовать одно сообщение для разных причин сбоя.
- Если метод сообщает ошибки полем возвращаемой структуры, заполнять его одинаково во всех ошибочных ветках.

## Логирование

- Сообщение описывает, что произошло и почему: вместе с исходом — условие или причина, а не только значение флага.
- Однотипные события — один шаблон сообщения, один набор атрибутов, один уровень.
- Ранний выход и пропуск по бизнес-условию логируются с причиной.
- В сообщении указываются Id сущностей, по которым принято решение.
- Параметры не логируются повторно на смежных уровнях стека: запись — в методе, где принимается решение.
- В аргументы лога и в `Logger.WithProperty` не передавать значение, которое в ветке заведомо `null`.
- Логирование создания или поиска сущности — внутри самого метода, без дублирования у вызывающего.
- Персональные данные, содержимое документов, сообщений и подписей в лог не писать: только Id и метаданные для диагностики.
- Тексты сообщений логирования не выносить в ресурсы локализации: литералы у вызова логгера.
- При переименовании метода и изменении логики обновлять тексты логов.
- Логирование ФП и АО — см. `rx-background-jobs` и `rx-async-handlers`.
