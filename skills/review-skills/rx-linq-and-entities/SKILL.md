# LINQ, коллекции, сущности и стоимость обращений

## LINQ и коллекции

- Цепочки методов: `.Where().Select().ToList()`.
- Наличие — `Any()`, пустота — `!Any()`; `Count() > 0` и `Count() == 0` не использовать.
- Метод возвращает пустую коллекцию, а не `null`.
- Не материализовать запрос раньше времени: оставлять `IQueryable`, чтобы фильтрация шла в БД. Методы, которые только собирают запрос, возвращают `IQueryable`, а не `List`.
- `.Contains()` по коллекции транслируется в `in (:id1, ...)`: лимит параметров 64000 для `int`/`long`/`Guid` и 2100 для `string`. Приведение других типов через `.ToList()` лимит не обходит. Перед `.Contains()` в предикате `GetAll` исходную коллекцию материализовать в `List`.
- Минимизировать обходы коллекции. Если повторный поиск неизбежен, использовать `Dictionary`/`HashSet`, а не повторные `.Where()`/`.FirstOrDefault()` (O(n) вместо O(n²)).
- **Запросы к репозиторию (`GetAll`, `Get`) внутри цикла запрещены (N+1):** грузить связанные сущности пакетно по идентификаторам и сопоставлять в памяти. Платформенный кэш пакетную загрузку не заменяет. Построение гиперссылок и прочие не расходные вызовы в цикле допустимы.
- `AsEnumerable()` без необходимости не вызывать: он не материализует данные и не предотвращает повторных обращений к БД. Для загрузки в память — явное `ToList()`/`ToArray()`.
- Известный Id и сущность обязана существовать → `Get(id)`, а не `GetAll(...).FirstOrDefault()` с ручным `throw`. Сущность может отсутствовать, нужен мягкий выход → `GetAll(...)` + `FirstOrDefault()`, а не `Get(id)`.
- Для количества или наличия — `Any()`/`Count()` на `IQueryable`, не загружать весь набор.
- `IQueryable`, используемый более одного раза, материализовать одним `ToList()`/`ToArray()`. Отложенный LINQ материализовать до мутации данных, от которых он зависит.
- В запросах к БД не применять `Trim()` и другую нормализацию строк: нормализовать при сохранении.
- Несколько сортировок — `OrderBy` + `ThenBy`, а не несколько `OrderBy`. Фильтр до сортировки: `Where` перед `OrderBy`.
- Проверка наличия элемента — `Contains`, а не `Any(x => x == value)`.
- У материализованных коллекций — свойство `Count`, а не `Count()`. На `IQueryable` — `Count()`.
- Пустой `IEnumerable` перед `foreach` не проверять.
- Если промежуточный список идентификаторов пуст, сразу вернуть пустой результат.
- В запросах сущностей с жизненным циклом явно фильтровать по статусу в том же `Where`.
- Нужны только идентификаторы — `Select(x => x.Id)`.
- Одной модели может соответствовать несколько записей → API возвращает коллекцию, а не `First`.
- Независимые условия, склеенные через `&&` в длинном предикате, разбивать на цепочку `Where` (кроме in-memory коллекции).

## Строки

- `IsNullOrWhiteSpace`, а не `IsNullOrEmpty` (если пробелы не значимы).
- Текстовые свойства перед сохранением `Trim()`; если после обрезки пусто — сохранять пустое значение.
- В цикле не склеивать строки через `+` — `StringBuilder`; его пустоту проверять через `Length`.
- Строка составного форматирования соответствует числу и типам аргументов (для `string.Format` и форматирующих методов `Logger`; у сгенерированных `Resources.{Ключ}Format(...)` аргументы типизированы, ошибку поймает компилятор).

## Сущности и приведение типов

- Получение, создание, удаление — через репозиторий (`Sungero.Company.Employees.GetAll(...)`, `Employees.Create()`). В экземплярных функциях текущий экземпляр — `_obj`.
- Проверка и приведение типов — `Is()` и `As()` репозитория, а не C#-приведения. Не передавать GUID типа, если проверка возможна через `Is()`.
- Не приводить сущность к служебным платформенным интерфейсам без обоснования; исключение — `((Sungero.Domain.Shared.IExtendedEntity)entity).Params`.
- Локализованное имя типа — из метаданных (`_obj.Info`).
- После `Create()` использовать GUID, сгенерированный платформой, не вызывать `Guid.NewGuid()` повторно. `new Guid()` создаёт пустой идентификатор: новый — `Guid.NewGuid()`, пустой — `Guid.Empty`.
- Если от сохранённого состояния зависят последующие операции — явный `Save`. В клиентском коде при присвоении свойств `Save()` не вызывать, если сохранение отложено на пользователя.
- Перед логикой, зависящей от изменения значения, сравнивать исходное и текущее значения, а не полагаться только на `IsChanged`. Для типов с `OriginalValue` использовать `_obj.State.Properties.{Свойство}.OriginalValue`.
- Значения перечислений и скаляры сравнивать через `==`; `Equals` — только для ссылок на сущности. В LINQ сравнивать значение перечисления, а не `.Value`.
- Перед обращением к членам потенциально nullable-ссылки — проверка на null; перед `.Value` у nullable — тоже. После API, которое при отсутствии объекта бросает исключение (`Get`), проверку на null не добавлять. Если по валидному Id сущность обязана существовать — бросить прикладное исключение, а не продолжать с null.
- Не сравнивать `a?.X == b?.Y`, если два `null` не должны считаться равными.
- При создании не дублировать присвоение значений по умолчанию, уже задаваемых в обработчике `Created`.
- `IGrouping` не нужен, если ключ группировки не используется: `IEnumerable` или `List`.
- `AccessRights.AllowRead` — только когда осознанно нужна выборка без фильтрации по правам.
- Поиск по внешнему идентификатору ограничивать областью владения (ящик, тенант, организация).

## Стоимость обращений

- Не материализовать сущности, если нужны идентификаторы или отдельные поля: платформа создаёт объект, разворачивает связи и проверяет права. Возвращать проекцию (`Select(x => x.Id)`, структура), а не `List<I{Сущность}>`. Если результат нужен только для подсчёта или наличия — число или флаг.
- `.Remote.` в цикле не вызывать: передавать весь набор за один вызов. Клиенту возвращать ровно нужное для отображения (структуру, а не коллекцию сущностей).
- Набор, не ограниченный по природе (все документы, задания, элементы очереди), выбирать с явным лимитом или постранично.
- Не запрашивать данные «про запас»; нужные в редкой ветке — получать внутри ветки.
- Одни и те же данные в одной операции не запрашивать повторно: верхний метод вычисляет один раз и передаёт вниз параметром или полем структуры.
