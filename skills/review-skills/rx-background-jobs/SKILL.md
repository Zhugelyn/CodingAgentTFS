# Фоновые процессы (ФП)

**Как распознать:** метод `public virtual void {Имя}()` без параметров в `ModuleJobs.cs` серверного проекта. Расписание и включённость задаются в метаданных и в коде не видны.

## Архитектура

- ФП — метод `public virtual void` в `partial class ModuleJobs`.
- Метод — оркестратор: проверка предусловий, логирование запуска и завершения, делегирование в `Functions.Module` / `PublicFunctions.Module`. Тяжёлая логика не пишется inline, а выносится в `ModuleServerFunctions`.
- Длительную обработку большого числа записей отдавать асинхронным обработчикам (`AsyncHandlers.*.ExecuteAsync()`): ФП только ставит задачи в очередь (см. `rx-async-handlers`).
- Создание элементов очереди и запуск АО — отдельные шаги: метод формирования очереди сам не вызывает `ExecuteAsync`.

## Логирование

- Начало и окончание логируются с именем ФП: `"MyJob. Start."` / `"MyJob. Done."`.
- Штатный ход — `Debug`; исключения — `Error` / `ErrorFormat` с полным объектом `ex`.
- Логируются ранние выходы (нет лицензии, нет данных) и итоговые счётчики (размер батча, число обработанных).
- При большом объёме записей — именованный логгер `Logger.WithLogger("MyJob")`.

## Транзакции

- Цепочка действий с сущностями в транзакции, чтобы не получить частичное изменение состояния.
- Транзакция оборачивает батч, а не весь ФП: `Transactions.Execute(() => { ... })`.
- Результат `Transactions.Execute` проверять; при неудаче батч пропускается с логом, обработка продолжается.

## Ошибки и блокировки

- Исключения перехватывать на уровне элемента или батча, а не всего ФП.
- При пагинации через `skip/take` сдвиг на следующий батч — в `finally`, чтобы исключение не остановило цикл.
- Перед изменением сущности проверять `Locks.GetLockInfo(entity).IsLocked`; заблокированную пропускать с логом. Для изменения сущности в фоне — блокировка через `TryLock`; не получили — прекратить обработку.

## Пагинация и ограничения

- `GetAll()` без лимита на потенциально большом наборе не использовать — только батчи.
- Размер батча — именованная константа в `ModuleConstants`; при необходимости переопределяется параметром БД с fallback на константу.
- В циклах `while(true)` — верхний предел итераций (`MaxIterations`); при достижении логировать.
- Если ФП запускает АО параллельно, ограничивать их число: считать записи очереди в статусе `InProcess`, вычитать из лимита и брать только свободные слоты (`Take(freeSlots)`).

## Предусловия запуска

- Обработка только новых данных с прошлого запуска — паттерн `GetLastAgentRunDate` / `UpdateLastAgentRunDate`.
- Перед запуском АО проверять отсутствие дубля в очереди (`HasSimilarQueueItemInProcessing` или `AsyncHandlerId`).
- Проверка лицензии на модуль — в самом начале метода: ранний `return` с логом.
- При изменении критериев выборки в заданиях с повторяемыми побочными эффектами (уведомления и т. п.) исключать уже обработанные сущности.
- Не переводить сущность в новое состояние жизненного цикла сразу после импорта или заполнения без проверок: только после подтверждения валидности, полноты данных и успешного сохранения.
- В конвейере со статусами различать первый запуск и повторную обработку: признак retry нельзя выводить только из статуса `InProcess`.
