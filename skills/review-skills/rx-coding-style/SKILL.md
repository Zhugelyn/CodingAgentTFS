# Стиль прикладного кода

Пороги (45 строк, 5 параметров, 3 уровня вложенности) — конвенции команды, а не требования платформы. Платформенные идентификаторы (`_obj`, `e`, `args` и др., см. `rx-platform-types`) правилам этого skill не подчиняются.

## Именование

- Методы и свойства — PascalCase, описательно (`GetDocumentResponsibleEmployee`). Переменные описательные.
- Имена на английском. Исключение — имена собственные внешних систем, форматов, стандартов (`Diadoc`, `Sbis`, `Kontur`). Русский текст в строковых литералах (сообщения логов) допустим.
- Без опечаток и без смешения латиницы и кириллицы в одном идентификаторе (включая омоглифы).
- Имя метода не повторяет целиком имя класса (`OfficialDocumentFunctions.GetOfficialDocumentAuthor` — плохо). Упоминание домена (`GetDocumentSummary`) допустимо.
- Нельзя имена, отличающиеся только регистром (кроме свойства и его поля).
- Аббревиатура из 3+ букв: `Dics`, а не `DICS`; из двух — обе заглавные (`IO`, `AI`); `Id`/`Ids` — исключение. Не относится к именам обработчиков, производным от кодов свойств метаданных (`TRRCValueInput`, `SWIFTValueInput`): их переименовать нельзя.
- Тип не делать частью имени параметра, кроме суффикса структуры данных (`employeeList` для `List<Employee>`).
- Односимвольные имена — только счётчики циклов (`i`, `j`, `k`) и параметры лямбд.
- Объект исключения в единственном `catch` — `ex`.
- Обработчики действий и парные `Can*` начинать с глагола (`StartGenerateText` / `CanStartGenerateText`).
- Глаголы: `Get…` — возврат данных, `Create…` — создание, `Validate…` — проверка. Для показа UI — `Show`, `View` только для просмотра содержимого.
- `Try*` — только если вызывающий получает признак успеха (`bool` + `out`/`result` или структура `IsSuccess` + данные). `Try*` с возвратом `void` или только данных — ошибка.
- Связанные API, параметры, константы и ресурсы одной функциональности называть согласованно по корню, числу и составу слов; не вводить синонимы для одного понятия и не смешивать разные термины в одном имени.
- Булевы — с `Is`/`Has` и той же временной семантикой, что у результата (`IsProcessing` / `IsProcessed`). Не вводить пары `IsX` / `IsNotX`.
- Идентификатор называть по источнику: `ExternalId`, `EmployeeId`, а не просто `Id`, если из контекста не очевидно.
- Размерность — в имени: `DefaultTimeoutInHours`, `PeriodInSeconds`.
- Константы имён параметров — суффикс `ParamName`; значение по умолчанию — `DefaultValue`.
- Методы с `[ExpressionElement]` — суффикс `NoCode` (`GetIntValueNoCode`); исключение — методы общего назначения, которые лишь используются из NoCode (`IsModuleValidByLicense`).
- Имя метода не заканчивается «висячим» предлогом (`With`, `By`, `For`); имена платформы/LINQ (`OrderBy`, `GroupBy`) — исключение.
- Не включать в имя детали текущей реализации.
- Пассивные конструкции (`Is`/`MustBe`) — с причастием (`Generated`), а не инфинитивом.

## Синтаксис

- `var` вместо явного типа.
- Вызовы нестатических методов **своего класса** — с `this`. Фасады (`Functions.*`, `PublicFunctions.*`, `IsolatedFunctions.*`) — без `this`.
- `string.Empty` вместо `""`; готовые константы (`int.MaxValue`, `EventArgs.Empty`, `Guid.Empty`). Исключение — значения по умолчанию параметров и атрибутов, где `string.Empty` не константа компиляции.
- Не использовать `List<T>.ForEach` — цикл `foreach`.
- Обычный `bool` не сравнивать с `true`/`false`. Для `bool?` — `== true` / `!= true` или `GetValueOrDefault()`.
- После ветвления, где все ветки завершаются `return`, `else` не оставлять.
- Вложенные `using` объединять в stacked using без вложенных блоков, каждый на своей строке с одним отступом.
- Явное условие цикла вместо `while (true)` с `break`. Исключение — пагинация в ФП и АО (см. `rx-background-jobs`).
- Если длинный путь (к константам, структурам, типам библиотеки) повторяется в файле 3+ раза — using-алиас.
- Перегрузки располагать рядом по возрастанию числа параметров.

## Сложность и читаемость

- Вложенность не более 3 уровней блоков (`if`, `foreach`, `while`, `try`): иначе подметоды или ранний выход.
- Метод не длиннее 45 строк.
- Без вложенных тернарных операторов (`??` и `?.` не считаются).
- Не усложнять там, где есть простой способ.
- Проверки и ранние выходы — от дешёвых к дорогим: признаки и права → запросы `GetAll()` → `.Remote.` → версии и тела документов (`LastVersion`, `Body.Read()`) → связанные сущности.
- Условие с 4+ операторами `&&`/`||` — в именованную локальную переменную (`shouldX`, `canY`, `isZ`).
- Булев параметр не должен переключать независимые сценарии: если тело распадается по флагу на две ветки без общего кода, сделать два метода. Флаг, влияющий на детали одного сценария, допустим.
- Ветвление базового метода по типу наследника — в `virtual`/`override` (см. `rx-function-design`).

## Дублирование

- Повторяющуюся логику — в общий метод. Перегрузки не копируют друг друга: одна делегирует другой.
- Вхождение в роль или группу — `IncludedIn(...)`, права — `AccessRights.Can*`, а не ручной перебор `RecipientLinks`. Ручная фильтрация по `Status` — принятая идиома.
- Общее родственных типов — в базовый тип (свойства задаются в метаданных, то есть в Studio).
- Не оставлять `override`, не зависящий от специфики наследника. Заготовки DS в `*Actions.cs` и `*Handlers.cs` с телом `base.{Метод}(e)` допустимы.
- Исправляя дефект в одном из однотипных модулей (`ExchangeCoreDiadoc` / `ExchangeCoreSbis`, UI-модули `*UI`), проверить аналоги и исправить в том же изменении, если расхождение не обосновано.

## Параметры

- Не более 5 параметров; логическая модель данных — прикладная структура.
- В параметрах методов передавать интерфейсы (`IEmployee`, `IOfficialDocument`), а не конкретные реализации.
- Нет неиспользуемых параметров (кроме заданных платформой: `e`, `args`).
- Не передавать то, что можно получить из других аргументов или свойств объекта, если это не требует дорогой операции и не вредит понятности.
- Работа с текущим экземпляром — `_obj`/`this`, а не он же отдельным аргументом. Фасадные вызовы `Functions.{Сущность}.X(_obj, ...)` — по контракту платформы.
- Не добавлять параметры только ради логирования. Исключение: сквозной `loggerPrefix` для корреляции записей.
- `AsyncHandlerInvokeArgs` и прочие АО-типы в Shared не передавать: разбор аргументов остаётся в `ModuleAsyncHandlers` или серверных модульных функциях.
- Метод, возвращающий созданный или найденный объект, не `void` (`CreateEmployee` → `IEmployee`). Исключения: обработчики действий, инициализатор модуля (`CreateRoles()`), методы запуска АО.
- `GetOrCreate` всегда возвращает сущность либо бросает исключение.
- В публичных методах сохранять валидацию входных данных, даже если вызывающие уже отфильтровали.

## Чистота кода

- Нет закомментированного кода, неиспользуемых переменных, пустых `catch`.
- Новый неиспользуемый метод — ошибка, кроме точек входа платформы: обработчики, действия, ФП, АО, `[Public]`, `[Remote]`, `[ExpressionElement]`, `virtual`-точки расширения.
- Пустой метод — реализовать или удалить. Не относится к заготовкам DS: блоки схемы маршрута (`StartBlock{N}`, `EndBlock{N}`, `StartAssignment{N}`, `StartNotice{N}`, `CompleteAssignment{N}`, `StartReviewAssignment{N}`), обработчики в `*Actions.cs` и `*Handlers.cs`, `virtual` с пустой базой, `override`, намеренно отключающий поведение базы.
- Удаляя функциональность, удалять связанные комментарии, ресурсы и константы.
- Не добавлять во входные структуры и DTO производные поля, которые используются один раз и целиком вычисляются из переданного (если вычисление не дорогое и результат не используется многократно).
- После `Create()` не присваивать свойству явный `null`. К прикладным структурам не относится: там каждое свойство ставится отдельно.
- `throw`/`catch` в одном методе не заменяют `if`/`return` для ожидаемых ситуаций.
- Не присваивать переменную самой себе; в цепочке `if`/`else if` нет повторяющихся условий и веток с одинаковым телом.

## Документация и комментарии

- У всех прикладных методов в `ModuleFunctions` и `{Сущность}Functions` есть XML-документация: инфинитив («Получить…», «Проверить…»), точка в конце, в `summary` одна короткая фраза, особые случаи — в `remarks`.
- Документация соответствует имени и поведению метода; при переименовании и смене логики обновлять её и тексты логов.
- Без орфографических ошибок.
- Комментарий объясняет причину, ограничение или бизнес-правило, а не пересказывает код. У неочевидного раннего возврата или пустой ветки — причина пропуска.
- TODO: `// TODO <ЛогинАвтора> <Текст>`; если отложено — номер задачи или бага.
- Обход бага платформы: `// HACK` с номером бага или эскалации.
- Суффикс `Attribute` опускать: `[Public]`, а не `[PublicAttribute]`.
