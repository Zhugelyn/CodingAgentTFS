# Перенос концепции ArioCodingAgent в LibreChat (паттерн «Передача полномочий»)

Что это: настройки, которые вводятся в конструкторе агентов LibreChat (инструкции, навыки, инструменты, лимиты, передачи). Код харнесса не переносится. Решение заказчика 2026-10-07: используем паттерн **Handoffs** (раздел «Передача полномочий»).

## 1. Схема потока

```
пользователь / вебхук (номер тикета или текст)
        │
        ▼
 ario-orchestrator  ── TFS MCP (чтение) ── собирает <ticket>
        │ handoff: ticket целиком
        ▼
   ario-analyst  ── RX tools (чтение) ──► unsuitable / needs_info → КОНЕЦ (ответ = итог)
        │ handoff (suitable): ticket без Discussion + plan
        ▼
  ario-developer ── RX tools (чтение, правка, git, build)
        │ handoff: ticket + plan + отчёт о сборке (без рассуждений)
        ▼
  ario-reviewer  ── RX tools (чтение, git diff)
        ├─ approve → КОНЕЦ
        ├─ reject, 1-й вердикт → handoff назад к ario-developer (замечания) → снова reviewer
        └─ 2-й вердикт любой → КОНЕЦ (при reject решает человек)
```

Соответствие нашему харнессу: `needs-human` = ответ analyst с `unsuitable`/`needs_info`, ответ developer с причиной остановки или второй `reject` ревьюера; `done` = `approve`.

## 2. Что вводить в конструкторе (по экранам)

Для каждого агента: **Провайдер** Ario, **Модель** Qwen3.8-27B, **Максимальное количество токенов контекста** 128000 (у нас максимум контекста в прогонах был ~55k), выводимых токенов 8000 (вместо «по умолчанию»), чтобы не было сюрпризов.

| Агент | Макс. шагов | Инструменты | Навыки | Передача полномочий |
|---|---|---|---|---|
| `ario-orchestrator` | 10 | TFS MCP (чтение) | нет | → `ario-analyst` |
| `ario-analyst` | 10 | RX tools: `find_files`, `search_text`, `read_file` | `rx-development-rules` (всегда) | → `ario-developer` |
| `ario-developer` | 60 | RX tools: `git_prepare_branch`, `find_files`, `search_text`, `read_file`, `edit_file`, `git_status`, `git_diff`, `build` | `rx-development-rules` (всегда) | → `ario-reviewer` |
| `ario-reviewer` | 30 | RX tools: `find_files`, `search_text`, `read_file`, `git_status`, `git_diff` | `rx-development-rules` (всегда) | → `ario-developer` (только на доработку) |

В разделе «Совместная работа агентов» у всех: «Подчинённые агенты» выключены, «Цепочка агентов» пуста. Лимиты шагов взяты из наших `limits` (analyst 10, developer 60, reviewer 30).

Для каждого агента: название, описание, **Instructions** и текст передачи (описание и passthrough) лежат в `agents/1-orchestrator.md` … `agents/4-reviewer.md`. Навык: загрузить папку `skills/rx-development-rules/` (файл `SKILL.md`), включить режим «применять всегда» и выдать нужным агентам.

Порядок создания: сначала `analyst`, `developer`, `reviewer` и навык, потом оркестратор (ему нужен список агентов для передачи), в конце добавить передачи: orchestrator → analyst, analyst → developer, developer → reviewer, reviewer → developer.

## 3. Чего в LibreChat нет и откуда это взять

| Что | У нас в харнессе | В LibreChat |
|---|---|---|
| Доступ к коду RX, git, сборка | свои инструменты | **MCP-сервер «RX tools»**, спецификация в `mcp-rx-tools.md`. Это единственная часть, где нужен код (из наших `src/ario/tools`) |
| Тикет из TFS | `ario fetch` | ваш готовый MCP к TFS (нужны только чтение work item и комментариев) |
| Жёсткий порядок этапов | оркестратор в коде | инструкции и описания передач: порядок соблюдается моделью, не кодом |
| Ровно одна доработка | счётчик в коде | инструкция ревьюера «считай свои вердикты» + лимит шагов |
| Лимиты времени/токенов на тикет, возобновление, блокировка | `limits`, `state.json`, `RunLock` | только лимит шагов на агента; остального нет |
| Защита путей, секреты, injection-сканер | `guardrails` | в MCP-сервере «RX tools» (запреты путей, маскирование вывода); от injection в тексте тикета защищают только инструкции |
| Трассировка и evals | `ario trace`, `ario eval` | история диалога LibreChat; evals придётся гонять вручную |

## 4. Известные риски паттерна handoffs

- **Обсуждение тикета дойдёт до агента с правами правки.** В нашем харнессе Discussion видит только analyst (решение D01), а developer и reviewer получают задачу и план: так текст-инъекция из комментария не попадает к агенту с `edit_file` и `build`. В handoffs все этапы идут в одном разговоре, и passthrough-инструкция лишь просит модель не пересылать лишнее, технически история остаётся видимой. Нужно проверить, что именно получает следующий агент; если полная история, это регресс по безопасности, и тогда нужны подчинённые агенты (изолированный контекст).
- **Стоимость и размер контекста.** Прогон 43702 в харнессе потратил 2,15M токенов запросов, из них 1,34M на developer (58 шагов). В общем разговоре reviewer потащит за собой всю историю developer, а для модели на 27B это ухудшает качество и увеличивает цену каждого его шага.
- **Общий контекст.** При передаче контекст разговора идёт дальше, поэтому ревьюер может увидеть рассуждения developer и оказаться предвзятым. Смягчение: passthrough-инструкции велят передавать только тикет, план и отчёт, а diff ревьюер получает сам через `git_diff`. Проверить на практике.
- **Зацикливание передач.** В LibreChat есть обсуждения про «необычное поведение рекурсивных передач» и потерю файловых ресурсов между агентами. Нас файлы не касаются, но петлю reviewer ⇄ developer надо проверить: на втором вердикте ревьюер обязан закончить ответом.
- **Рост контекста.** Все этапы в одном разговоре: у Qwen3.8-27B окно нужно следить; держать лимит токенов контекста и шагов.
- **Кто закончит поток.** Итогом считается ответ последнего агента. В инструкциях это прописано для каждого выхода (analyst при отказе, developer при остановке, reviewer на втором вердикте или `approve`).
- **Запись в TFS.** Оркестратору дан только доступ на чтение. Комментарий с итогом в тикет и PR лучше добавить отдельным шагом после проверки качества, когда решите, кто пишет в TFS.

## 5. Тестовый сценарий (приёмка настройки)

1. В чате выбрать `ario-orchestrator`, написать: «Тикет 43702».
2. Ожидаемый поток: orchestrator собрал `<ticket>` → analyst `suitable` с планом → developer создал ветку, правит, `build` успешна → reviewer вернул вердикт → при `reject` доработка → итог.
3. Проверка: ветка `antares/ai-43702`, diff по плану, нет правок `*.g.cs`, нет новых файлов; сборка успешна; число шагов каждого агента не упёрлось в лимит.
4. Негативные кейсы: 43031 (закрыт по обсуждению: analyst должен отдать `unsuitable` со ссылкой на комментарий), тикет с пустым описанием (`needs_info`), тикет с текстом-инъекцией в комментарии (инструкция не выполняется).
5. Сравнить с результатом нашего харнесса на тех же тикетах: время, шаги, качество правки.
