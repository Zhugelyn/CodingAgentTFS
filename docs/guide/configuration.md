# Настройка

Всё, что настраивается в `.env` и конфигурационных файлах. Быстрый старт: [README](../../README.md).

## Переменные `.env`

Образец: `config/.env.example`.

| Переменная | Что это |
|---|---|
| `RX_PATH` | Путь к репозиторию RX |
| `BASE_BRANCH` | Ветка, от которой создаётся ветка тикета (по умолчанию `master`) |
| `BRANCH_TEMPLATE` | Имя ветки тикета, обязателен `{id}`, например `antares/ai-{id}` |
| `ARIO_BUILD_COMMAND` | Штатная команда сборки RX (Directum Launcher: `do dirx build`) |
| `OPENROUTER_API_KEY` | Ключ OpenRouter |
| `LLM_MODEL` | Модель по умолчанию (формат LiteLLM, например `openrouter/qwen/qwen3.8-27b`) |
| `ANALYST_MODEL`, `DEVELOPER_MODEL`, `REVIEWER_MODEL` | Модель по ролям; пусто: берётся `LLM_MODEL` |
| `TFS_URL`, `TFS_PROJECT`, `TFS_PAT` | Доступ к TFS (PAT с правом Work Items: Read) |
| `TFS_WIQL`, `TFS_MAX_ITEMS` | Свой запрос отбора и лимит тикетов за один `fetch` (необязательно) |
| `TFS_WRITE`, `TFS_WRITE_PAT`, `ARIO_TICKET_FLOW` | Запись на доску: включатель, токен записи, файл потока состояний (раздел «Запись на доску» ниже) |
| `ARIO_PUBLISH` | Включает push и PR (раздел «Push и PR» ниже), нужен блок `publish` в профиле |
| `ARIO_WEBHOOK_SECRET`, `ARIO_WEBHOOK_HOST`, `ARIO_WEBHOOK_PORT` | Вебхуки TFS (`ario watch --webhook`): пароль Basic, адрес и порт приёмника (README, раздел про вебхуки) |
| `ARIO_POLL_MINUTES` | Как часто `ario watch` опрашивает TFS, минут (по умолчанию 5) |
| `rework_started` в `ticket-flow.yaml` | Состояние на доске при доработке по замечаниям (`ario rework`) |
| `ARIO_REPOS` | Файл профилей репозиториев (раздел «Несколько репозиториев» ниже); без него работает профиль из `RX_PATH` |
| `ARIO_BOARD` | Файл конфигурации доски: доска TFS и её репозитории с потоками состояний (раздел «Конфигурация доски» ниже); заменяет `TFS_URL`, `TFS_PROJECT`, `TFS_WIQL`, `TFS_MAX_ITEMS`, `ARIO_TICKET_FLOW`, `ARIO_REPOS` |
| `ARIO_OTLP_ENDPOINT`, `ARIO_OTLP_LLM_CONTENT` | Графики и живая выгрузка запросов в Phoenix ([phoenix.md](phoenix.md)) |

`.env` в репозиторий не попадает. Секреты (`OPENROUTER_API_KEY`, `TFS_PAT`) нигде, кроме `.env`, не хранятся.

Перед запуском рабочее дерево RX должно быть **чистым**: иначе тикет не будет взят.

## Настройка поведения агентов

| Что менять | Где |
|---|---|
| Роли агентов | `agents/<роль>/AGENTS.md` и `agents/<роль>/tools.yaml` |
| Общие правила RX | `AGENTS.md` в корне |
| Навыки по RX | `skills/<имя>/SKILL.md` |
| Лимиты шагов, времени, контекста, запрещённые пути, правила injection | `config/guardrails.yaml` |

Время и зависания: `limits.ticket_timeout_seconds` (30 минут на тикет) проверяется между шагами
агента, а каждый запрос к модели отдельно ограничен жёстким пределом
`limits.model_call_timeout_seconds` (420 с) и остатком времени тикета. Если запрос не завершился,
срабатывает обычный повтор, а после исчерпания повторов этап останавливается с причиной «Сбой
модели».

## Конфигурация доски (один файл вместо россыпи переменных)

Файл `ARIO_BOARD` (образец `config/board.yaml.example`) описывает доску TFS, откуда берутся
тикеты, и репозитории, которые она обслуживает. Принцип: **одна доска на машину**, репозитории
принадлежат доске.

- `board`: адрес и проект, запрос отбора (`query`), `max_items`, имена переменных с токенами
  (`pat_env`, `write_pat_env`), общий поток состояний (`flow`), типы тикетов для проверки потока
  (`work_item_types`).
- `repositories`: профили, как в `repos.yaml` (путь клона, ветки, сборка, `match`, `publish`), плюс
  `flow` (свой поток состояний репозитория; пусто: поток доски) и `description`.
- Токены в файле не хранятся, только имена переменных. Включатели записи `TFS_WRITE` и
  `ARIO_PUBLISH` остаются в `.env`.
- С `ARIO_BOARD` настройки доски берутся из файла и перекрывают `TFS_URL`, `TFS_PROJECT`, `TFS_WIQL`,
  `TFS_MAX_ITEMS`, `ARIO_TICKET_FLOW`; вместе с `ARIO_REPOS` файл задавать нельзя (ошибка при
  старте). Без `ARIO_BOARD` работает прежняя схема из `.env`.
- Поток тикета выбирается так: `flow` его репозитория → `flow` доски → без смены состояний.
- Поток сверяется с состояниями типов доски при старте `run`, `watch`, `rework`: неизвестное имя
  состояния в `to` или `from` выводится предупреждением, а не молчаливым пропуском на тикете.

В правилах потока (`ticket-flow.yaml.example`) `from` принимает имена, `*` и
`category:<категория TFS>` (Proposed, InProgress, Resolved, Completed, Removed). У типа Bug на
доске Antares: Proposed: New, Analysis, TechDesign, ReadyForDev, ToDo; InProgress: Development;
Resolved: Acceptance, ReadyForTesting, Testing, Finalizing; Completed: Closed. Целевое
состояние (`to`) задаётся именем: в категории их несколько.

Адреса `http(s)://` в комментариях на доске записываются кликабельными ссылками (ссылка на PR в
итоговом комментарии).

## Запись на доску (комментарии и состояния)

Оркестратор может писать в тикеты TFS: переводить состояние по ходу работы и оставлять итоговый
комментарий (при остановке с отметкой автора тикета). Пишутся только тикеты, пришедшие из TFS
(`ario fetch`); тикеты из папки не трогаются.

1. В `.env`: `TFS_WRITE=1` и токен записи в `TFS_WRITE_PAT` (права Work Items: Read & write; без
   него пишет `TFS_PAT`). Без `TFS_WRITE` ничего не меняется, а в трассу попадает только пометка
   «запись выключена».
2. Состояния: `ARIO_TICKET_FLOW=config/ticket-flow.yaml` (образец `config/ticket-flow.yaml.example`).
   Агент меняет состояние, только если оно сейчас из списка `from`: если человек уже передвинул
   карточку, она остаётся как есть.
3. Результат записи видно в `uv run ario trace <id> --steps` и в `events.jsonl` (событие
   `ticket_system`). Сбой записи прогон не останавливает: запросы к доске идут с коротким
   таймаутом без повторов, а после двух сбоев подряд запись прекращается до конца прогона.
4. Переход `review_approved` (в ReadyForTesting) в образце закомментирован: включайте его вместе с
   push и PR, иначе тикет попадёт тестировщикам, пока изменения лежат в локальной ветке.
5. Пишутся тикеты с `source: tfs` в файле (так их создаёт `ario fetch`). Не кладите в `inbox/`
   вручную файлы с `source: tfs` и чужим номером: комментарии и состояния уйдут в тикет с этим
   номером на доске.

## Push и PR

После одобрения ревью оркестратор может сам закоммитить правки, отправить ветку тикета и открыть
PR (этап `publish`). По умолчанию выключено, включается двумя вещами:

1. `ARIO_PUBLISH=1` в `.env`.
2. Блок `publish` в профиле репозитория (образец в `config/repos.yaml.example`): адрес
   git-сервера, проект, репозиторий, целевая ветка PR и имя переменной окружения с токеном
   (`pat_env`, например `RX_GIT_PAT`; сам токен в файл не пишется). Скоуп токена: Code, Read &
   write. Пользователю токена в репозитории нужны права Contribute, Create branch и Contribute to
   pull requests; политики целевой ветки (обязательные ревьюеры, сборка) PR не отменяют.

Как это работает: push идёт без force и только в ветку тикета, токен передаётся переменными
окружения (его нет в адресе remote и в аргументах процесса). Повторный запуск после сбоя ничего не
дублирует: пустой коммит не создаётся, существующий активный PR переиспользуется. Адрес PR пишется
в `runs/<id>/publish.json`, в описание PR попадают ссылка на тикет, план, отчёт разработчика и
вердикты ревью. Состояние тикета после открытия PR задаёт событие `pr_created` в потоке состояний.
Если у ветки нет коммитов или текущая ветка не ветка тикета, этап останавливается и тикет уходит
к человеку.

### Тикеты и код на разных серверах

Номер тикета принадлежит серверу доски (`TFS_URL`); на сервере кода (`publish.url`) тот же номер
означает совсем другой work item. Поэтому:
- запись в тикет (комментарии, состояния) идёт только на сервер доски, а ссылка на PR записывается
  в тикет как обычный адрес;
- клиент сервера кода умеет только PR и не умеет work items (и наоборот): действие чужой роли
  отклоняется до отправки запроса;
- PR не привязывается к work items сервера кода, а `#123` и `AB#123` в тексте коммита, заголовка и
  описания PR заменяются на `№123` (иначе TFS сделал бы ссылку на чужой элемент); в описании PR
  тикет указан адресом на сервере доски.

Если на целевой ветке сервера кода включена политика «обязательна связь с work item», PR
не пройдёт её: связать нечем, и это нужно решать политикой, а не подстановкой чужого номера.

## Несколько репозиториев

Репозитории описываются профилями в файле, путь к которому задан в `ARIO_REPOS` (образец:
`config/repos.yaml.example`; сам по себе файл рядом ничего не включает). В профиле: путь клона, базовая ветка, шаблон ветки, команда
сборки, папка знаний (`AGENTS.md`, `agents/`, `skills/`; относительный путь считается от
`ARIO_PROJECT_DIR`, а `path` — от папки файла), дополнительные запреты записи и правило
выбора (`match`: префикс area path и теги).

- Профиль выбирается один раз на тикет и записывается в `runs/<id>/state.json`; `resume`
  продолжает на том же репозитории.
- Явный выбор: `uv run ario run <id> --repo <имя>`.
- Не подошёл ни один профиль: берётся `default`. Подошло два: тикет остаётся в `inbox/` с
  комментарием, выберите репозиторий через `--repo`.
- Без `ARIO_REPOS` ничего менять не нужно: работает профиль `rx` из `.env`.

Не коммитить: `.env`, `runs/`, `traces/`, содержимое `tickets/*/`.
