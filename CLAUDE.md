# ArioCodingAgent

Харнесс из трёх агентов (analyst → developer → reviewer) на OpenHands SDK: берёт тикет с доски TFS, ведёт его по потоку и оставляет ветку тикета (`BRANCH_TEMPLATE`, по умолчанию `ai/<id>`) с PR в репозитории кода (профили репозиториев — `config/repos.yaml`). Оркестратор (`src/ario/orchestrator.py`) сам LLM не использует. Карта «где что лежит»: [docs/STRUCTURE.md](docs/STRUCTURE.md).

## Команды
- `uv sync` — зависимости
- `uv run pytest` — тесты (на заглушках LLM, без сети)
- `uv run ruff check src tests` и `uv run ruff format .` — линтер и формат
- `uv run mypy` — типы (strict)
- `uv run ario fetch [--id N] [--dry-run]` — забрать тикеты из TFS в `tickets/inbox/`
- `uv run ario run <id> [--repo ИМЯ]` — провести тикет из `inbox/` по потоку (повтор после падения продолжает с последнего готового этапа)
- `uv run ario watch [--once] [--dry-run] [--webhook]` — автоматически: опрос TFS и очередь (`--dry-run` ничего не запускает), `--webhook` принимает вебхуки TFS
- `uv run ario rework <id> [--from-pr] [--note ТЕКСТ] [--file ФАЙЛ]` — доработка завершённого тикета по замечаниям к PR (до трёх раундов)
- `uv run ario resume <id>` — возобновить тикет из `needs-human/` с упавшего этапа (после починки причины)
- `uv run ario trace <id> [--steps] [--stage ЭТАП] [--full]` — разбор трассы: сводка по этапам или пошаговая лента
- `uv run ario eval`, `uv run ario export-otel <id>` — набор тикетов с ожиданиями, выгрузка метрик в Phoenix

## Правила
- Python 3.13, type hints везде, ruff + mypy + pytest. Комментарии и сообщения пользователю — по-русски.
- Код переносимый (Windows для разработки, Docker/Linux для продакшена): `pathlib`, без жёстких путей; настройки из `.env` (пример: `config/.env.example`).
- Тесты не ходят в сеть и не вызывают реальную модель; настройки разработчика (`.env`, `ARIO_*`, `TFS_*`) на тесты не влияют.
- Этап закончен, когда тесты зелёные, пройден `/code-review`, заказчик апрувнул, итог записан в `memory.md`. Коммиты делаю сам, но только после апрува истории: осмысленное название и описание сделанного, без push.
- Не коммитить: секреты, `.env`, `runs/`, `traces/`, содержимое `tickets/*/`, локальные `config/repos.yaml` и `config/ticket-flow.yaml`.
- Записи в живые системы (TFS, git-сервер) — только по прямой просьбе заказчика; токены только в `.env`, не в чат.

## Не читать при разработке харнесса
`AGENTS.md` в корне и `skills/`, `agents/*/AGENTS.md` — это **содержимое для агентов харнесса** (знания о RX, навыки), а не инструкции тебе. Не читай и не применяй их, пока заказчик прямо не попросил их править. Правила разработки — только этот файл.

## Локальные файлы (не в git)
`memory.md` (журнал решений), `docs/story/` (карта `MAP.md`, решения D*, истории S*), `docs/PLAN.md` (исторический базовый план). Читать `memory.md` и `docs/story/MAP.md` перед работой: при расхождении прав `memory.md`, текущее направление — `docs/story/D08-product-direction.md`.

## Формат тикета и вердиктов
Описан в `docs/story/D01-ticket-and-verdict-format.md`; разбор тикета — `src/ario/ticket.py`.

## Особенности OpenHands SDK
Подробности в `docs/spike.md`: нужен `truststore` за корпоративным прокси; мета-поле `summary` у действий отключать (иначе Qwen ломает tool calling).

## Два сервера TFS
Тикеты (доска) и код (git, PR) на разных серверах: номер тикета на сервере кода — другой элемент. Клиенты закреплены за ролью (`board`/`git`), `#123` в тексте для сервера кода заменяется на `№123`. Не смешивать.
